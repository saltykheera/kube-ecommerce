# Days 10 & 11 Implementation: Integration, Security & Fault Tolerance

## Phase 1: Kubernetes NetworkPolicies (Zero-Trust Cluster Security) — Completed

### 1. Architectural Security Boundaries
We implemented 6 zero-trust Kubernetes NetworkPolicies in `helm/ecommerce-stack/templates/networkpolicy.yaml`:

1. **`allow-gateway-to-mcp-upstreams`**:
   - Upstream MCP Servers (`mcp-woocommerce`, `mcp-calculator`, `mcp-metrics`) accept ingress **only from the Gateway pod**. Direct access from the public internet, Ingress, dashboard, or other upstreams is blocked.
   - `mcp-woocommerce` is permitted egress to `wordpress:80` for WooCommerce REST API calls.

2. **`allow-gateway-to-postgres`**:
   - Gateway PostgreSQL database accepts ingress **only from the Gateway pod** (port 5432).
   - Direct database access from frontend dashboard, WordPress, or upstreams is completely blocked.

3. **`allow-wordpress-to-mariadb`**:
   - Storefront MariaDB database accepts ingress **only from WordPress** (port 3306).
   - Direct database access from the Gateway, dashboard, or upstreams is blocked.

4. **`gateway-boundary-policy`**:
   - Ingress permitted only from Traefik Ingress (external requests) and the Dashboard pod (internal `/api` proxy).
   - Egress restricted to PostgreSQL, upstream MCP pods, CoreDNS (port 53), and external HTTPS (port 443) for Gemini AI API calls.

5. **`dashboard-boundary-policy`**:
   - Ingress permitted from Traefik Ingress (port 80).
   - Egress restricted to Gateway (port 8000) and CoreDNS (port 53).

6. **`wordpress-boundary-policy`**:
   - Ingress permitted from Traefik Ingress (port 80) and `mcp-woocommerce` (port 80).
   - Egress restricted to MariaDB (port 3306), CoreDNS (port 53), and external HTTPS/HTTP for WordPress updates.

## Phase 2: Chaos & Fault-Tolerance Testing — Completed

### 1. Chaos Scenarios Tested
We implemented an automated chaos testing suite in `scripts/test-chaos-fault-tolerance.sh` verifying all resilience criteria:

1. **Hard Upstream Failure (Dead Pod)**:
   - Scaled `mcp-calculator` to 0 replicas.
   - **Result**: Gateway tool discovery returned 8 remaining tools in **0.12s** (non-blocking partial discovery). The gateway process did not crash or hang.
2. **Registry Health State Tracking**:
   - `GET /api/servers` live-probed upstreams with a 3.5s timeout.
   - **Result**: `mcp-calculator` was automatically marked `status: "unreachable"` in PostgreSQL and rendered as degraded with timeout metrics in the React dashboard.
3. **Fault Containment (Zero Cascade)**:
   - Executed live tool `metrics__get_sales_target` on living upstream: **HTTP 200 OK**.
   - Executed dead tool `calc__calculate`: returned immediate structured JSON-RPC error. Gateway process remained healthy.
4. **Self-Healing & Auto-Recovery**:
   - Scaled `mcp-calculator` back to 1 replica.
   - **Result**: Tool discovery restored all 11 tools automatically without restarting the Gateway pod. Subsequent call to `calc__calculate` succeeded (`Result: 200.0`).
5. **Dynamic Admin Disabling vs Upstream Failure**:
   - Disabled `metrics` server via `PATCH /api/servers/3`.
   - **Result**: Tools instantly dropped from 11 to 8 without downtime; re-enabling restored all tools immediately.
6. **Pod Resiliency & Storage Persistence**:
   - Killed active WordPress pod (`kubectl delete pod`).
   - **Result**: Kubernetes ReplicaSet spawned a replacement pod in 25s. The storefront returned HTTP 200 OK with all MariaDB PVC catalog and order data completely intact.
